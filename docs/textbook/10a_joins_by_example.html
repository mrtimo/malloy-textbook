Chapter 10a: Joins by Example

Open in Notebook Viewer ▶ Open in VS Code

Chapter 10 covered joins in full. This chapter is the gentle, hands-on version. In every exercise the code is already written for you, except one line: the join. You type that line, run the cell, and watch new columns appear.

🐢 No pressure. Every exercise follows the same three steps:

  1. Before: run a query on one table. Notice what's missing.

  2. ✏️ Your turn: type one join_one: line where it says // ✏️ your line.

  3. After: run it again. Same rows, same totals, new columns.

How the ✏️ cells work

  • In your notebook (VS Code or github.dev), each ✏️ cell has a blank line that says // ✏️ type your join line here. Replace that comment with the join line, then run the cell.

  • On this website you can see the finished line, marked // ✏️ your line, and the result it should give you. Use it to check your work.

  • If you run a ✏️ cell before typing your line, you'll get an error like 'users' is not defined. That's fine! It just means Malloy doesn't know about the other table yet. That's exactly what the join line fixes.

What is a join?

The store keeps its data in separate tables, like separate sheets in a workbook:

Table One row per… Some columns
items item sold sale_price, created_at, user_id, inventory_item_id
users customer id, first_name, state, gender, age
inventory physical item in the warehouse id, product_category, product_brand, product_department
states U.S. state state_name, region

The items table doesn't contain the customer's name. It only has a user_id: a number that points to one row in the users table. A join tells Malloy: "to find the customer for this item, look up user_id in the users table." If you've used VLOOKUP or XLOOKUP in Excel, a join is the same idea.

Setup: four tables, no joins yet

Run this cell first. It defines the four tables, with no joins. (The textbook's ecommerce.malloy file already has the joins written in. Here we start from scratch so you can add them yourself.)

source: items is duckdb.table('data/order_items.parquet') extend {
  primary_key: id
  measure:
    item_count is count()
    # currency
    total_sales is sale_price.sum()
}

source: users is duckdb.table('data/users.parquet') extend {
  primary_key: id
  measure: user_count is count()
}

source: inventory is duckdb.table('data/inventory_items.parquet') extend {
  primary_key: id
}

source: states is duckdb.table('data/state_regions.csv') extend {
  primary_key: state_name
}

Notice the primary_key: line in each source. It names the column that is different for every row, such as a customer's id. A join looks rows up by that key.

The join recipe

Every join you write answers three questions:

Question Exercise 1 example
1. Which table do I want to bring in? users
2. Which of my columns points to it? user_id
3. Does each of my rows have one match? Then it's join_one. Each item has one customer

Put the answers together:

join_one: users with user_id

If the columns are named differently, or the other table's column isn't its primary key, use on and write the match out:

join_one: states on state = states.state_name

When something goes wrong

What you see What it means Fix
'users' is not defined The query uses users.something, but there's no join Add the join_one: line
'user_id' is not defined You used a column name that isn't in your table Check the spelling. Run select: * with limit: 5 to see the column names
Names or categories that look random The join matched the wrong column (for example with id instead of with user_id) Use the column that points to the other table
A row with ∅ (empty) values Some rows had no match in the other table Often fine (like the UK customers). Check that the key columns really match

Key takeaways

  • A join brings another table's columns into your source. It works like VLOOKUP.

  • join_one: users with user_id means: each row has one user, found by matching user_id to the user's primary key.

  • Use joined columns with a dot: users.state, inventory.product_category.

  • A join_one adds columns, not rows, and doesn't change your totals.

  • A source can have several joins, and joins can chain: users_with_region_2.states.region.

  • Use on when the matching columns have different names: join_one: states on state = states.state_name.
