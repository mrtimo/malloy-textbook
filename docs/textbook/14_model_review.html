Chapter 14: Anatomy of a Malloy Model

Open in VS Code

You've now met every major part of a Malloy model. This last chapter puts them all together in one file, names_full.malloy (it's in the malloy-textbook-notebooks folder), and walks through it section by section. Use this chapter as a review and as a checklist when you build your own models.

import "names_full.malloy"

1. Compiler flags 

##! experimental.givens

##! lines at the top of a file turn on compiler features for that file. Only experimental features need them. Right now that's givens (and, in older versions, things like partition_by:).

2. Documentation

A model is read by people, by the Explorer, and more and more by AI assistants. Two kinds of documentation help them:

  • // comments are for people reading the code: why a choice was made, what a section is for. The compiler ignores them.

  • #" descriptions attach to the next object (a source, field, view, or given). Tools can read them: the Explorer shows them when you hover over a field, and AI tools that query the model see them too.

#" U.S. baby names: one row per state, gender, birth year, and name (1910–2021).
#" Source: U.S. Social Security Administration. Names given to fewer than 5
#" babies in a state and year are not included.
source: names is duckdb.table('data/usa_names.parquet') extend {
  dimension:
    #" The decade a baby was born in, e.g. 1990.
    decade is floor(year_born / 10) * 10

💡 Good descriptions say what a field means, not what the code does. "Births to girls" is better than "sum of births where gender = F." Also note the grain ("one row per...") and the source of the data on every source.

3. Givens 

given:
  #" Two-letter code of the state the `home_state_names` source focuses on.
  HOME_STATE :: string is 'OR'

source: home_state_names is names extend {
  where: state = $HOME_STATE
}

The model declares the values it needs from outside, near the top where they're easy to find. Here home_state_names follows whatever HOME_STATE is set to:

run: home_state_names -> by_name + { where: year_born = 2021, limit: 5 }

4. Sources

A model usually has three kinds of sources:

  • Base sources read a table or file: duckdb.table('data/usa_names.parquet'), or the CSV duckdb.table('data/state_regions.csv').

  • SQL sources run any SQL your database understands: duckdb.sql("SELECT ...") (Chapter 9).

  • Query sources are built from another source's query: name_summary is names -> {...} extend {...} (Chapter 12).

Any of them can be extended with fields, joins, and views.

run: name_summary -> {
  where: lifetime_births > 100000
  group_by: gender
  aggregate:
    summary_name_count
    # number="0.0"
    avg_years_in_use is years_in_use.avg()
}
QUERY RESULTS 
[
  {
    "gender": "F",
    "summary_name_count": 339,
    "avg_years_in_use": 101.45132743362832
  },
  {
    "gender": "M",
    "summary_name_count": 289,
    "avg_years_in_use": 106.9757785467128
  }
]
WITH __stage0 AS (
  SELECT 
     base."name" as "name",
     base."gender" as "gender",
     (COALESCE(SUM(base."number"),0)) as "lifetime_births",
     min(base."year") as "first_year",
     max(base."year") as "last_year"
  FROM 'data/usa_names.parquet' as base
  GROUP BY 1,2
  ORDER BY 3 desc NULLS LAST
)
SELECT 
   base."gender" as "gender",
   COUNT(1) as "summary_name_count",
   AVG(((base."last_year"-base."first_year")+1)) as "avg_years_in_use"
FROM __stage0 as base
WHERE base."lifetime_births">100000
GROUP BY 1
ORDER BY 2 desc NULLS LAST

5. Primary keys and joins 

source: states is duckdb.table('data/state_regions.csv') extend {
  primary_key: state_code
}

source: names is duckdb.table('data/usa_names.parquet') extend {
  join_one: states on state = states.state_code
  dimension: region is states.region
  ...
}

states is a small dimension table: one row per state, with its Census region and division. Every names row matches exactly one state, so it's a join_one. The primary key lets symmetric aggregates count each state once (Chapter 10). Promoting states.region to a dimension called region makes the most useful joined field easy to find.

run: names -> {
  where: year_born = 2021
  group_by: region, states.division
  aggregate: total_births, states.state_count
  order_by: region
}

6. Renames, dimensions, and measures

  • Renames fix awkward raw column names: rename: year_born is `year`.

  • Dimensions are per-row values you group by and filter on: decade, name_length, generation.

  • Measures are aggregates. Good models include:

    • base measures: total_births, name_count

    • filtered measures for common slices: girls, boys (Chapter 8)

    • ratio measures using all(): share_of_births, births_per_100k (Chapter 11)

Because they live in the model, every query, notebook, and Explorer session uses the same definitions:

run: names -> {
  group_by: generation
  aggregate:
    total_births, girls, boys, share_of_births
    # hidden
    first_year is min(year_born)
  order_by: first_year
}

WITH __stage0 AS (
  SELECT
    group_set,
    CASE WHEN group_set=1 THEN
      CASE WHEN (base."year"<1928) THEN 'Greatest (1910–1927)' WHEN (base."year"<1946) THEN 'Silent (1928–1945)' WHEN (base."year"<1965) THEN 'Boomer (1946–1964)' WHEN (base."year"<1981) THEN 'Gen X (1965–1980)' WHEN (base."year"<1997) THEN 'Millennial (1981–1996)' WHEN (base."year"<2013) THEN 'Gen Z (1997–2012)' ELSE 'Gen Alpha (2013– )' END
      END as "generation__1",
    CASE WHEN group_set=1 THEN
      COALESCE(SUM(base."number"),0)
      END as "total_births__1",
    (CASE WHEN group_set=1 THEN
      COALESCE(SUM(CASE WHEN base."gender"='F' THEN base."number" END),0)
      END) as "girls__1",
    (CASE WHEN group_set=1 THEN
      COALESCE(SUM(CASE WHEN base."gender"='M' THEN base."number" END),0)
      END) as "boys__1",
    (CASE WHEN group_set=1 THEN
      COALESCE(SUM(base."number"),0)
      END)*1.0/MAX((CASE WHEN group_set=0 THEN
      COALESCE(SUM(base."number"),0)
      END)) OVER () as "share_of_births__1",
    CASE WHEN group_set=1 THEN
      min(base."year")
      END as "first_year__1"
  FROM 'data/usa_names.parquet' as base
  CROSS JOIN (SELECT UNNEST(GENERATE_SERIES(0,1,1)) as group_set  ) as group_set
  GROUP BY 1,2
)
SELECT
  "generation__1" as "generation",
  MAX(CASE WHEN group_set=1 THEN "total_births__1" END) as "total_births",
  MAX(CASE WHEN group_set=1 THEN "girls__1" END) as "girls",
  MAX(CASE WHEN group_set=1 THEN "boys__1" END) as "boys",
  MAX(CASE WHEN group_set=1 THEN "share_of_births__1" END) as "share_of_births",
  MAX(CASE WHEN group_set=1 THEN "first_year__1" END) as "first_year"
FROM __stage0
WHERE group_set NOT IN (0)
GROUP BY 1
ORDER BY 6 ASC NULLS LAST

(The # hidden tag keeps first_year out of the display, but the query can still sort by it, so the generations come out in time order instead of alphabetically.)

💡 Limiting what users see. In a bigger model, you may want to hide helper fields. accept: a, b, c keeps only the listed fields, and except: x, y removes fields. See Limiting access to fields.

8. Views

Views are the model's ready-made answers. names_full.malloy has every kind:

  • simple views: by_name, by_year, by_region

  • a dashboard view made of nests: name_report

  • a multi-stage view with window calculations: names_for_half_by_decade

A dashboard view plus refinement gives a whole report in one line:

run: names -> name_report + { where: name = 'Harper' }
QUERY RESULTS 
[

WITH __stage0 AS (
  SELECT
    group_set,
    CASE WHEN group_set=1 THEN
      COALESCE(SUM(base."number"),0)
      END as "total_births__1",
    (CASE WHEN group_set=1 THEN
      COALESCE(SUM(CASE WHEN base."gender"='F' THEN base."number" END),0)
      END) as "girls__1",
    (CASE WHEN group_set=1 THEN
      COALESCE(SUM(CASE WHEN base."gender"='M' THEN base."number" END),0)
      END) as "boys__1",
    CASE WHEN group_set=2 THEN
      base."year"
      END as "year_born__2",
    CASE WHEN group_set=2 THEN
      COALESCE(SUM(base."number"),0)
      END as "total_births__2",
    CASE WHEN group_set=3 THEN
      states_0."region"
      END as "region__3",
    CASE WHEN group_set=3 THEN
      COALESCE(SUM(base."number"),0)
      END as "total_births__3",
    (CASE WHEN group_set=3 THEN
      COALESCE(SUM(base."number"),0)
      END)*1.0/MAX((CASE WHEN group_set=1 THEN
      COALESCE(SUM(base."number"),0)
      END)) OVER () as "share_of_births__3",
    CASE WHEN group_set=4 THEN
      states_0."state_name"
      END as "state_name__4",
    CASE WHEN group_set=4 THEN
      COALESCE(SUM(base."number"),0)
      END as "total_births__4"
  FROM 'data/usa_names.parquet' as base
   LEFT JOIN 'data/state_regions.csv' AS states_0
    ON base."state"=states_0."state_code"
  CROSS JOIN (SELECT UNNEST(GENERATE_SERIES(0,4,1)) as group_set  ) as group_set
  WHERE base."name"='Harper'
  GROUP BY 1,5,7,10
)
, __stage1 AS (
  SELECT
    *,
   CASE WHEN GROUP_SET=4 THEN
                 ROW_NUMBER() OVER (PARTITION BY group_set ORDER BY  "total_births__4" desc) END  as __row_number__4 
  FROM __stage0
)
, __stage2 AS (
  SELECT * FROM __stage1
   WHERE  NOT ((GROUP_SET = 4 AND __row_number__4 > 5))
)
SELECT
  MAX(CASE WHEN group_set=1 THEN "total_births__1" END) as "total_births",
  MAX(CASE WHEN group_set=1 THEN "girls__1" END) as "girls",
  MAX(CASE WHEN group_set=1 THEN "boys__1" END) as "boys",
  COALESCE(LIST({
    "year_born": "year_born__2", 
    "total_births": "total_births__2"}  ORDER BY  "year_born__2" ASC NULLS LAST) FILTER (WHERE group_set=2),[]) as "by_year",
  COALESCE(LIST({
    "region": "region__3", 
    "total_births": "total_births__3",

FROM __stage2

A checklist for your own models

When you build a model, run through this list:

  1. ☐ Every source has a #" description that says what one row is and where the data comes from.

  2. ☐ Every table you join has a primary_key:.

  3. ☐ Awkward raw columns are renamed, and messy columns are cleaned in dimensions (Chapter 9).

  4. ☐ The important business numbers are measures, with filtered and ratio versions of the common ones.

  5. ☐ Number formats (# currency, # percent) are on the measures, not repeated in every query.

  6. ☐ Common questions are views, and one dashboard view gives a quick overview.

  7. ☐ Values that should change at run time are givens, declared near the top.

  8. ☐ Notebooks import the model, and contain narrative and questions, not definitions (Chapter 5).

Key takeaways

  • A Malloy model is a set of documented sources, each with joins, dimensions, measures, and views, plus optional givens and named queries.

  • Logic lives in one place (the model), so every notebook, the Explorer, and every app agree on what the numbers mean.

  • Document with // for people reading code and #" for tools and users.
