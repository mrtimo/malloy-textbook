Chapter 14a: Building a Semantic Model, Step by Step

Open in Notebook Viewer ▶ Open in VS Code

So far you've mostly used models that were already written (names.malloy, ecommerce.malloy). In this chapter you'll grow one yourself, starting from a pile of plain queries. The process is called refactoring: you rewrite your code so it's shorter, clearer and easier to reuse, without changing any of the answers.

You'll refactor in four passes:

  1. Measures: name the aggregates you keep retyping.

  2. Dimensions: name the row-level calculations you keep retyping.

  3. Views: name the whole queries you keep rewriting.

  4. Nesting: combine those views into rich reports and dashboards.

Then you'll document the model, move it into its own .malloy file, and import it. The homework asks you to do the same thing with your own dataset.

What is a semantic model, and why bother?

A semantic model is a layer that sits between the raw table and the people (or AI assistants) asking questions. It gives business concepts a name and one definition: what counts as a "late flight," what "revenue" means, which date a "year" refers to.

Without a model, every analyst writes those definitions again in every query, and they drift apart. Here's a small example. Two people are asked, "What share of flights were late?"

source: flights_raw is duckdb.table('data/flights.parquet')
// Analyst A: late means the plane LEFT more than 15 minutes late
run: flights_raw -> {
  aggregate: pct_late is count() { where: dep_delay > 15 } / count()
}

Both queries are "correct," but they give different answers to the same question. Put both in a report and someone will notice, and then nobody trusts either number.

A model settles it once. The U.S. Department of Transportation counts a flight as late when it arrives 15 or more minutes after schedule, so that's the definition we'll write into the model. After that, every query, dashboard, and AI assistant that uses the model gets the same answer.

💡 This is exactly why Claude could answer questions about SEC filings correctly through the open10k connector: someone had already defined revenues, net_margin and filer_status in a model, so Claude didn't have to guess.

Expression Kind How many times you typed it
count() aggregate 5 (and 6 more inside pct_late and pct_cancelled)
count() { where: arr_delay > 15 } / count() aggregate 4
arr_delay.avg() aggregate 2

🧭 The refactoring rule. If you've typed an expression twice, give it a name and move it into the model. If it's a definition (like "late" or "long flight"), move it in even if you've only typed it once.

Step 1: refactor the measures

A measure is a named aggregate: something that summarizes many rows into one number (count(), .sum(), .avg(), and anything built from them).

What to do:

  1. Make a list of every aggregate expression in your queries (the table above is that list).

  2. Give each one a clear, consistent name. Good conventions:

    • _count for counts: flight_count

    • total_ for sums: total_distance

    • avg_ for averages: avg_arr_delay

    • pct_ for shares: pct_late

  3. Put each one in a measure: inside the source's extend { } block.

  4. Build measures out of other measures. pct_late is just late_flight_count / flight_count, so define the two counts first and divide them. If someone later changes how flights are counted, pct_late follows automatically.

  5. Add a render tag such as # percent above shares, so the formatting comes with the measure wherever it's used.

  6. Rewrite your queries to use the new names, and check that the numbers haven't changed.

Here's the source with the measures refactored. We'll call it flights_v1 so you can compare it with the raw table.

source: flights_v1 is duckdb.table('data/flights.parquet') extend {
  measure:
    flight_count is count()
    total_distance is distance.sum()
    avg_arr_delay is arr_delay.avg()
    avg_dep_delay is dep_delay.avg()

    late_flight_count is count() { where: arr_delay > 15 }
    cancelled_count is count() { where: cancelled = 'Y' }

    # percent
    pct_late is late_flight_count / flight_count
    # percent
    pct_cancelled is cancelled_count / flight_count
}

Step 2: refactor the dimensions

A dimension is a named, row-level calculation: it produces one value per flight, and you can group_by it or filter on it. Booleans, buckets, cleaned-up text and date parts are all dimensions.

What to do:

  1. List every row-level expression in your queries: anything inside a group_by: or a where: that's more than a bare column name.

  2. Look for hidden dimensions inside your measures. arr_delay > 15 appears inside late_flight_count. That test is really a yes/no fact about each flight, so it deserves its own name: is_late.

  3. Name booleans with is_ (is_late, is_cancelled), so filters read like English: where: is_late.

  4. Turn awkward codes into readable values. cancelled holds 'Y' or 'N' text; is_cancelled is a real true/false.

  5. Use rename: for columns whose names are cryptic. id2 and tail_num become flight_id and tail_number.

  6. Set a primary_key: if the table has one. You'll need it for joins.

  7. Go back and simplify the measures so they use the new dimensions.

Here's flights_v2. Lines marked // ✚ are new since flights_v1.

source: flights_v2 is duckdb.table('data/flights.parquet') extend {
  rename:                                              // ✚
    flight_id is id2
    tail_number is tail_num
  primary_key: flight_id                               // ✚

  dimension:                                           // ✚ all of these
    is_late is arr_delay > 15
    is_cancelled is cancelled = 'Y'
    is_diverted is diverted = 'Y'
    route is concat(origin, ' → ', destination)
    dep_hour is hour(dep_time)
    distance_band is distance ?
      pick '1 · under 500 mi' when < 500
      pick '2 · 500–1,499 mi' when < 1500
      else '3 · 1,500+ mi'

  measure:
    flight_count is count()
    total_distance is distance.sum()
    avg_arr_delay is arr_delay.avg()
    avg_dep_delay is dep_delay.avg()

    late_flight_count is flight_count { where: is_late }        // ✚ simpler
    cancelled_count is flight_count { where: is_cancelled }     // ✚ simpler

    # percent
    pct_late is late_flight_count / flight_count
    # percent
    pct_cancelled is cancelled_count / flight_count
}

Step 3: refactor the views

A view is a named query that lives inside the source (Chapter 3). If you find yourself writing the same group_by + aggregate + order_by again and again, that's a view.

What to do:

  1. Look at your original queries. Each one that you'd want to run again becomes a view. Name it after what it groups by: by_carrier, by_year, top_routes.

  2. Keep views small and focused: one grouping, a few measures, a sensible sort and limit. Small views are easier to combine (Step 4).

  3. Put a chart tag above each view (# bar_chart, # line_chart). The tag travels with the view, so whenever you run or nest it, it draws as a chart.

  4. Use your measures and dimensions inside the views, never raw expressions. Views are built on the model, not around it.

source: flights_v4 is flights_v3 extend {
  view: by_carrier is {
    group_by: carriers.nickname
    aggregate: flight_count, avg_arr_delay, pct_late
    order_by: flight_count desc
  }

  # line_chart
  view: by_year is {
    group_by: yr is dep_time.year
    aggregate: flight_count
    order_by: yr
  }

  # bar_chart
  view: top_routes is {
    group_by: route
    aggregate: flight_count
    limit: 10
  }

  # bar_chart
  view: late_by_hour is {
    group_by: dep_hour
    aggregate: pct_late
    order_by: dep_hour
  }

  # bar_chart
  view: late_by_distance is {
    group_by: distance_band
    aggregate: pct_late
    order_by: distance_band
  }
}

Step 5: document and tidy the model

A model is read by people, by the Explorer, and by AI assistants. Before you call it done:

  1. Add #" descriptions to the source and to any field whose meaning isn't obvious (Chapter 15). Say how something is defined: "late = arrived 15+ minutes after schedule."

  2. Name things for the reader. pct_late beats pl; distance_band beats db.

  3. Delete scratch fields you made while experimenting.

  4. Group the file: renames, then dimensions, then measures, then views, so a reader knows where to look.

Step 6: move the model into its own file

A model in a notebook only helps that notebook. To reuse it, move it into a .malloy file and import it (Chapter 5). The finished model is in flights.malloy, next to this notebook. It contains everything from Steps 1–5 in one source called flights, with descriptions. Open it and read it top to bottom; it should look familiar.

A refactoring checklist

Use this when you refactor your own data:

Pass Look for Turn it into Name it like
Measures the same aggregate typed twice measure: x_count, total_x, avg_x, pct_x
a ratio of two aggregates a measure built from measures pct_late is late_flight_count / flight_count
Dimensions a test inside a where: or a filtered measure a boolean dimension: is_late, is_cancelled
codes, buckets, date parts, combined columns dimension: with pick, concat, hour()… distance_band, route, dep_hour
a cryptic column name rename: flight_id is id2
a lookup table join_one: with a primary_key: carriers.nickname
Views a query you run more than once view: with a chart tag by_x, top_x, x_by_y
Nesting several views you look at together nest: or a # dashboard view carrier_report

And after every pass: re-run your original queries and confirm the numbers didn't change.

Key takeaways

  • A semantic model gives each business idea one name and one definition, so every query, dashboard and AI assistant gets the same answer.

  • Refactoring changes the code, not the answers. Check your numbers after every step.

  • Measures summarize many rows (count(), .sum(), .avg()). Build ratios out of other measures.

  • Dimensions have one value per row. Pull hidden tests out of filtered measures into is_ booleans.

  • Views are small, named queries. Put chart tags on them so they draw themselves wherever they're used.

  • Nesting views is where a model pays off: profiles, drill-downs and dashboards in a few lines.

  • Finish by documenting the model and moving it to a .malloy file you can import.
