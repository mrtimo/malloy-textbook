Chapter 10: Joins and Symmetric Aggregates

Open in VS Code

Real data is spread over several tables. Joins connect them. In SQL, joins are also the number-one source of wrong numbers, because joining a "one" table to a "many" table repeats rows, and sums and averages quietly double count. In this chapter you'll learn:

  • the shape of a star schema

  • join_one, join_many, and join_cross, and when to use each

  • how to reach joined fields with dot paths like users.state

  • why Malloy's symmetric aggregates give correct answers where naive SQL doesn't

  • how to join a table to a summary query of itself

The e-commerce star schema

A star schema has one central fact table (events: sales, clicks, births) surrounded by dimension tables (things: customers, products, places). In our store:

                  ┌──────────────┐
                  │    users     │  one row per customer
                  └──────▲───────┘
                         │ user_id
┌──────────────────────────────────────────┐
│               order_items                │  FACT: one row per item sold
└──────────────────────────────────────────┘
                         │ inventory_item_id
                  ┌──────▼──────────┐
                  │ inventory_items │  one row per physical item
                  └──────┬──────────┘
                         │ product_id
                  ┌──────▼───────┐
                  │   products   │  one row per catalog product
                  └──────────────┘

Here's how ecommerce.malloy describes it. (Each source also defines some measures, left out here.)

source: users is duckdb.table('data/users.parquet') extend {
  primary_key: id
}

source: products is duckdb.table('data/products.parquet') extend {
  primary_key: id
}

source: inventory_items is duckdb.table('data/inventory_items.parquet') extend {
  primary_key: id
  join_one: products with product_id
}

source: order_items is duckdb.table('data/order_items.parquet') extend {
  primary_key: id
  join_one: users with user_id
  join_one: inventory_items with inventory_item_id
}

Two things to notice:

  • Each source declares its primary_key:, the column that is unique for every row. Malloy needs it to do joins correctly.

  • join_one: users with user_id means "each order item has one user, found by matching my user_id to the user's primary key." That's the most common kind of join, and with is its shorthand.

Once a join is declared, you reach the joined table's fields with a dot: users.state, inventory_items.product_category. Joins can chain: inventory_items.products.brand goes two hops.

The three kinds of join

Join Read it as Example
join_one: each row of mine matches at most one row of theirs order item → its user
join_many: each row of mine can match many rows of theirs user → their order items
join_cross: many-to-many: lots of rows on both sides every product × every promotion

You can write a join's condition two ways:

join_one: users with user_id                          // my user_id = users' primary key
join_one: users on user_id = users.id                 // any boolean condition
join_many: order_items on id = order_items.user_id    // join_many always uses "on"

join_many: looking at the data from the customer's side

So far we started from order_items and looked "up" at users. To ask questions about customers, start from users and look "down" at their orders with join_many:

source: customers is users extend {
  join_many: order_items on id = order_items.user_id
  measure:
    # number="0.0"
    avg_age is age.avg()
}
run: customers -> {
  group_by: traffic_source
  aggregate:
    user_count
    avg_age
    order_items.order_item_count
    order_items.total_sales
}

The fan-out problem, and how Malloy avoids it

When you join a "one" table to a "many" table, the "one" rows get repeated, once per matching "many" row. A customer with 12 order items appears 12 times in the joined result. Any SUM, COUNT, or AVG over customer columns then counts that customer 12 times.

Let's prove it with plain SQL. This is the query most people would write first:

run: duckdb.sql("""
  SELECT
    u.traffic_source,
    COUNT(*)      AS user_count_WRONG,
    AVG(u.age)    AS avg_age_WRONG,
    COUNT(o.id)   AS order_item_count,
    SUM(o.sale_price) AS total_sales
  FROM 'data/users.parquet' u
  LEFT JOIN 'data/order_items.parquet' o ON o.user_id = u.id
  GROUP BY 1
  ORDER BY 2 DESC
""") -> {
  select: *
}

Compare with the Malloy result above. The SQL user_count_WRONG is inflated. It's counting order rows, not users. The SQL avg_age_WRONG is also off, and much harder to notice: it's a weighted average that gives frequent shoppers more weight. These are exactly the bugs that slip into real reports.

Malloy gets both right because of symmetric aggregates. Since every source has a primary key, Malloy knows which table each aggregate "belongs to". When it computes user_count or avg_age (measures of users) across a join that repeats users, it generates SQL that counts each user once, using the primary key to remove the repeats. You write the obvious query, and the number is right.

💡 "Locality" of an aggregate. Every aggregate is computed with respect to some source in the join graph. age.avg() written in customers averages over customers. order_items.sale_price.sum() sums over order items. The path in front of .avg() or .sum() tells Malloy where to aggregate.

Joining a source to a query

A join target doesn't have to be a table. It can be a query, which is great for adding context such as totals. Let's go back to the baby names. To compare a name with the total births in its state and year, first build a summary, then join it with a two-column match:

import "names.malloy"
source: state_year_totals is names -> {
  group_by: state, year_born
  aggregate: all_births is total_births
}

source: names_with_totals is names extend {
  join_one: sy is state_year_totals
    on state = sy.state and year_born = sy.year_born

  measure:
    # percent
    share_of_state_year is total_births / sy.all_births.sum()
}
run: names_with_totals -> {
  where: name = 'Emma', gender = 'F', year_born ~ f'[2015 to 2021]'
  group_by: year_born
  aggregate: total_births, sy.all_births.sum(), share_of_state_year
  order_by: year_born
}

WITH __stage0 AS (
  SELECT 
     base."state" as "state",
     base."year" as "year_born",
     (COALESCE(SUM(base."number"),0)) as "all_births"
  FROM 'data/usa_names.parquet' as base
  GROUP BY 1,2
)
SELECT 
   base."year" as "year_born",
   COALESCE(SUM(base."number"),0) as "total_births",
   COALESCE((
        SELECT SUM(a.val) as value
        FROM (
          SELECT UNNEST(list(distinct {key:sy_0."__distinct_key", val: sy_0."all_births"})) a
        )
      ),0) as "all_births",
   (COALESCE(SUM(base."number"),0))*1.0/COALESCE((
        SELECT SUM(a.val) as value
        FROM (
          SELECT UNNEST(list(distinct {key:sy_0."__distinct_key", val: sy_0."all_births"})) a
        )
      ),0) as "share_of_state_year"
FROM 'data/usa_names.parquet' as base
 LEFT JOIN (SELECT GEN_RANDOM_UUID() as "__distinct_key", x.*  FROM __stage0 as x) AS sy_0
  ON (base."state"=sy_0."state") and (base."year"=sy_0."year_born")
WHERE (base."name"='Emma')
AND (base."gender"='F')
AND (base."year" >= 2015  AND  base."year" <= 2021)
GROUP BY 1
ORDER BY 1 ASC NULLS LAST

Many names rows (one per name) match the same state_year_totals row. That's normal for join_one (many of mine → one of theirs). Because of symmetric aggregates, sy.all_births.sum() adds each state-year total only once, even though it was matched to many name rows.

join_cross: many-to-many

join_cross is for joins where both sides can have many matching rows, or where you want every combination. It's the least common join, but it's handy for "what-if" scenarios. Here we cross every 2022 sale with three hypothetical discount levels:

source: discount_scenarios is duckdb.sql("""
  SELECT * FROM (VALUES ('No discount', 0.0), ('10% off', 0.10), ('25% off', 0.25)) t(scenario, discount)
""")

source: what_if is order_items extend {
  where: created_at ~ f'2022'
  join_cross: s is discount_scenarios
  measure:
    # currency
    discounted_sales is total_sales * (1 - max(s.discount))
}
run: what_if -> {
  group_by: s.scenario
  aggregate: total_sales, discounted_sales
}
QUERY RESULTS 
[
  {
    "scenario": "10% off",
    "total_sales": 4744743.446900487,
    "discounted_sales": 4270269.102210439
  },
  {
    "scenario": "No discount",
    "total_sales": 4744743.446900487,
    "discounted_sales": 4744743.446900487
  },
  {
    "scenario": "25% off",
    "total_sales": 4744743.446900487,
    "discounted_sales": 3558557.585175365
  }
]
SELECT 
   s_0."scenario" as "scenario",
   COALESCE((
        SELECT SUM(a.val) as value
        FROM (
          SELECT UNNEST(list(distinct {key:base."id", val: base."sale_price"})) a
        )
      ),0) as "total_sales",
   (COALESCE((
        SELECT SUM(a.val) as value
        FROM (
          SELECT UNNEST(list(distinct {key:base."id", val: base."sale_price"})) a
        )
      ),0))*((1-max(s_0."discount"))) as "discounted_sales"
FROM 'data/order_items.parquet' as base
 LEFT JOIN (
  SELECT * FROM (VALUES ('No discount', 0.0), ('10% off', 0.10), ('25% off', 0.25)) t(scenario, discount)
) AS s_0
  ON 1=1
WHERE base."created_at" >= TIMESTAMP '2022-01-01 00:00:00' AND base."created_at" < TIMESTAMP '2023-01-01 00:00:00'
GROUP BY 1
ORDER BY 2 desc NULLS LAST

Every order item is paired with every scenario, so the raw joined data has 3× the rows. But look at total_sales: it's the same correct number in every row. It isn't tripled, because total_sales is an order_items measure, and symmetric aggregates count each order item once per group. Within each scenario group, max(s.discount) is just that scenario's discount (min and max are safe across any join, because repeated values don't change them), so discounted_sales is the correct sales total times the discount factor.

⚠️ Joins need primary keys. Symmetric aggregates depend on primary_key:. If you join a source that has no primary key and then aggregate its fields across a join_many or join_cross, Malloy can't protect you. Declare a primary key on every table you join.

Key takeaways

  • A star schema is a central fact table plus dimension tables. Declare a primary_key: on each.

  • join_one: x with fk is the common case (many-to-one). Use join_many: to look from the "one" side down at the "many" side, and join_cross: for many-to-many and scenarios.

  • Reach joined fields with dots: users.state, inventory_items.products.brand.

  • Naive SQL joins double count. Malloy's symmetric aggregates use primary keys to compute each measure at its own grain, so counts, sums, and averages stay correct.

  • You can join to a query (for example, a summary table), not just to a table.
