Chapter 12: Pipelines and Window Calculations

Open in VS Code

Some questions can't be answered in one pass over the data:

  • How many names does it take to cover half of all babies? First total each name, then add up the totals in order.

  • In which decade did each name peak? First find each name's best year, then group the names by that decade.

  • How did sales change from last month? First total each month, then compare each month with the one before it.

Malloy has two tools for this:

  • Pipelines (-> { } -> { }): the output of one query stage becomes the input to the next.

  • Calculations (calculate:): window functions like lag(), rank(), and running totals, computed on a query's results.

import "names.malloy"
import "ecommerce.malloy"

Pipelines: chaining query stages

You've been writing one-stage queries: source -> { ... }. Add another -> and another { }, and the second stage runs on the output of the first. The second stage can only see the first stage's output columns.

Question: how are name lengths distributed? First get each name's total births (stage 1), then count how many names there are of each length (stage 2):

run: names -> {
  where: year_born = 2021
  group_by: name, name_length
  aggregate: total_births
} -> {
  group_by: name_length
  aggregate:
    names is count()
    births is total_births.sum()
  order_by: name_length
}

Example: when did each name peak?

Stage 1: for each name and year, total the births. Stage 2: for each name, add up the lifetime total, find the biggest single year with max(), and use a nest with limit: 1 (sorted by births) to show which year that was:

run: names -> {
  where: gender = 'F'
  group_by: name, year_born
  aggregate: births is total_births
} -> {
  group_by: name
  aggregate:
    lifetime_births is births.sum()
    peak_births is births.max()
  nest: peak is {
    group_by: year_born
    aggregate: births_that_year is births.sum()
    order_by: births_that_year desc
    limit: 1
  }
  having: births.sum() > 100000
  order_by: lifetime_births desc
  limit: 10
}

     base."name" as "name",
     base."year" as "year_born",

, __stage1 AS (
  SELECT
    group_set,
    base."name" as "name__0",
    CASE WHEN group_set=0 THEN
      COALESCE(SUM(base."births"),0)
      END as "lifetime_births__0",
    CASE WHEN group_set=0 THEN
      max(base."births")
      END as "peak_births__0",
    CASE WHEN group_set=1 THEN
      base."year_born"
      END as "year_born__1",
    CASE WHEN group_set=1 THEN
      COALESCE(SUM(base."births"),0)
      END as "births_that_year__1",
    CASE WHEN group_set=0 THEN CASE WHEN CASE WHEN group_set=0 THEN
      COALESCE(SUM(base."births"),0)
      END>100000 THEN 0 ELSE 1 END END as __delete__0
  FROM __stage0 as base
  CROSS JOIN (SELECT UNNEST(GENERATE_SERIES(0,1,1)) as group_set  ) as group_set
  GROUP BY 1,2,5
)
, __stage2 AS (
  SELECT
    *,
   CASE WHEN GROUP_SET=0 THEN
                 ROW_NUMBER() OVER (PARTITION BY group_set, __delete__0 ORDER BY  "lifetime_births__0" desc) END  as __row_number__0,
  CASE WHEN GROUP_SET=1 THEN
                 ROW_NUMBER() OVER (PARTITION BY CAST("name__0" as VARCHAR), group_set ORDER BY  "births_that_year__1" desc) END  as __row_number__1 
  FROM __stage1
)
, __stage3 AS (
  SELECT
    *,
    MAX(CASE WHEN group_set IN (0,1) THEN __delete__0 + CASE WHEN (GROUP_SET = 0 AND __row_number__0 > 10) THEN 1 ELSE 0 END
                 END) OVER(PARTITION BY CAST("name__0" as VARCHAR)) as __shaving__0 
  FROM __stage2 WHERE  NOT ((GROUP_SET = 1 AND __row_number__1 > 1))
)
, __stage4 AS (
  SELECT *
  FROM __stage3
  WHERE NOT ((group_set IN (0,1) AND __shaving__0 > 0)
  )
)
SELECT
  "name__0" as "name",
  MAX(CASE WHEN group_set=0 THEN "lifetime_births__0" END) as "lifetime_births",
  MAX(CASE WHEN group_set=0 THEN "peak_births__0" END) as "peak_births",
  COALESCE(LIST({
    "year_born": "year_born__1", 
    "births_that_year": "births_that_year__1"}  ORDER BY  "births_that_year__1" DESC NULLS LAST) FILTER (WHERE group_set=1),[]) as "peak"
FROM __stage4
GROUP BY 1
ORDER BY 2 desc NULLS LAST
LIMIT 10

Each of these popular girls' names shows its peak year. Pipelines can be as long as you need, and each stage can use where:, group_by:, nest:, having:, and everything else.

Pipelines as sources

Name a pipeline's output as a source, and you can query it like a table, and even extend it with new fields. This is how you build reusable summary tables:

source: name_summary is names -> {
  group_by: name, gender
  aggregate:
    lifetime_births is total_births
    first_year is min(year_born)
    last_year is max(year_born)
    states_used is count(state)
} extend {
  dimension: years_in_use is last_year - first_year + 1
  measure: name_count is count()
}
run: name_summary -> {
  where: lifetime_births > 50000
  group_by: gender
  aggregate:
    name_count
    # number="0.0"
    avg_years_in_use is years_in_use.avg()
}
QUERY RESULTS 
[
  {
    "gender": "F",
    "name_count": 535,
    "avg_years_in_use": 97.30841121495327
  },
  {
    "gender": "M",
    "name_count": 450,
    "avg_years_in_use": 104.83777777777777
  }
]
WITH __stage0 AS (
  SELECT 
     base."name" as "name",
     base."gender" as "gender",
     (COALESCE(SUM(base."number"),0)) as "lifetime_births",
     min(base."year") as "first_year",
     max(base."year") as "last_year",
     count(distinct base."state") as "states_used"
  FROM 'data/usa_names.parquet' as base
  GROUP BY 1,2
  ORDER BY 3 desc NULLS LAST
)
SELECT 
   base."gender" as "gender",
   COUNT(1) as "name_count",
   AVG(((base."last_year"-base."first_year")+1)) as "avg_years_in_use"
FROM __stage0 as base
WHERE base."lifetime_births">50000
GROUP BY 1
ORDER BY 2 desc NULLS LAST

Query-local fields with extend:

Sometimes a field is only needed by one query. extend: inside the query defines dimensions or measures that exist just for that query, without changing the model:

run: names -> {
  extend: {
    dimension: is_double_letter_start is lower(substr(name, 1, 1)) = substr(name, 2, 1)
  }
  where: is_double_letter_start
  group_by: name
  aggregate: total_births
  limit: 5
}

Window calculations with calculate:

A calculation is computed on the rows of a query's result, after grouping and aggregating. Each row can look at other rows: the previous one, the running total so far, its rank. These are SQL's window functions, written in calculate:.

Function Meaning
lag(x) / lag(x, n) the value of x from the previous row (or n rows back)
lead(x) the value from the next row
rank() the row's rank (ties share a rank)
row_number() 1, 2, 3, ...
sum_cumulative(x) running total
avg_moving(x, n) average of this row and the n before it
sum_window(x) sum over all rows (handy for shares)
first_value(x) / last_value(x) the first or last value in the window

📘 Malloy docs. Calculations and window functions · Window function reference

lag: change from the previous row

Calculations follow the query's order_by:. Sort by time, and lag() means "the previous period":

run: order_items -> {
  where: created_at ~ f'2022'
  group_by: order_month is created_at.month
  aggregate: total_sales
  order_by: order_month
  calculate:
    # currency
    prev_month is lag(total_sales)
    # currency
    change is total_sales - lag(total_sales)
    # percent
    pct_change is total_sales / lag(total_sales) - 1
}

Running totals: sum_cumulative

How many names does it take to cover half of all babies born in 2021? Sort names from most to least popular, keep a running total, and compare it with the overall total, sum_window(). Then a second stage counts the rows that are still under 50%. That's a pipeline and a window function together:

run: names -> {
  where: year_born = 2021
  group_by: name
  aggregate: total_births
  order_by: total_births desc
  calculate:
    running_total is sum_cumulative(total_births)
    grand_total is sum_window(total_births)
} -> {
  where: running_total <= grand_total / 2
  aggregate: names_covering_half is count()
}
QUERY RESULTS 
[
  {
    "names_covering_half": 262
  }
]
WITH __stage0 AS (
  SELECT 
     base."name" as "name",
     COALESCE(SUM(base."number"),0) as "total_births",
     SUM((COALESCE(SUM(base."number"),0))) OVER(  ORDER BY  COALESCE(SUM(base."number"),0) desc NULLS LAST ) as "running_total",
     SUM((COALESCE(SUM(base."number"),0))) OVER(  ) as "grand_total"
  FROM 'data/usa_names.parquet' as base
  WHERE base."year"=2021
  GROUP BY 1
)
SELECT 
   COUNT(1) as "names_covering_half"
FROM __stage0 as base
WHERE base."running_total"<=(base."grand_total"*1.0/2)

Just 262 names (out of more than 30,000) cover half of all babies born in 2021. How has that changed over time? We can do several years at once by restarting the running total for each year with partition_by: (more on that below):

run: names -> {
  where: year_born = 1950 | 1980 | 2000 | 2021
  group_by: year_born, name
  aggregate: total_births
  calculate:
    running_total is sum_cumulative(total_births) {
      partition_by: year_born
      order_by: total_births desc
    }
    grand_total is sum_window(total_births) {
      partition_by: year_born
    }
} -> {
  where: running_total <= grand_total / 2
  group_by: year_born
  aggregate: names_covering_half is count()
  order_by: year_born
}
QUERY RESULTS 
[
  {
    "year_born": "1950",
    "names_covering_half": 53
  },
  {
    "year_born": "1980",
    "names_covering_half": 75
  },
  {
    "year_born": "2000",
    "names_covering_half": 144
  },

WITH __stage0 AS (
  SELECT 
     base."year" as "year_born",
     base."name" as "name",
     COALESCE(SUM(base."number"),0) as "total_births",
     SUM((COALESCE(SUM(base."number"),0))) OVER(PARTITION BY (base."year") ORDER BY (COALESCE(SUM(base."number"),0)) DESC ) as "running_total",

  FROM 'data/usa_names.parquet' as base
  WHERE base."year" IN (1950,1980,2000,2021)
  GROUP BY 1,2
)
SELECT 
   base."year_born" as "year_born",
   COUNT(1) as "names_covering_half"
FROM __stage0 as base
WHERE base."running_total"<=(base."grand_total"*1.0/2)
GROUP BY 1
ORDER BY 1 ASC NULLS LAST

In 1950, a few dozen names covered half of all babies. By 2021, it took hundreds. Parents have been choosing more and more varied names.

Moving averages

  order_by: order_month
  calculate: three_month_avg is avg_moving(total_sales, 2)

partition_by: restart the window for each group

By default, a calculation runs over all the rows of the result. partition_by: restarts it for each group. Here's a year-to-date running total that starts over every January:

run: order_items -> {
  where: created_at ~ f'2021 to 2023'
  group_by:
    order_year is created_at.year
    order_month is created_at.month
  aggregate: total_sales
  order_by: order_month
  calculate:
    # currency
    ytd_sales is sum_cumulative(total_sales) {
      partition_by: order_year
      order_by: order_month
    }
  limit: 15
}

⚠️ Calculations happen after where:. A calculate: only sees the rows that survived the query's filters. If you filter to 2022 and ask for lag(), January 2022 has no "previous month," even though December 2021 exists in the data. To compare with rows you don't want to show, compute in one stage and filter in the next stage of a pipeline.

Calculations vs. all()

Both give you numbers from "other rows." So which should you use?

all() / exclude() (Chapter 11) calculate:
aggregates ignoring grouping looks at other result rows
order doesn't matter order matters (lag, running totals)
can be used in measures and in later aggregates can't be aggregated in the same stage (use a pipeline)
shares, totals, contributions change from previous row, ranks, running totals, moving averages

Key takeaways

  • A pipeline (-> {...} -> {...}) feeds one stage's output into the next. Use it whenever a question needs "first summarize, then summarize again."

  • A pipeline can be turned into a source (source: x is s -> {...} extend {...}) or a multi-stage view.

  • extend: inside a query adds fields for just that query.

  • calculate: runs window functions on the result rows, following the query's order_by:: lag, lead, rank, row_number, sum_cumulative, avg_moving, sum_window...

  • partition_by: restarts a calculation for each group, and an order_by: inside the calculation sets its order separately from the result's order.
